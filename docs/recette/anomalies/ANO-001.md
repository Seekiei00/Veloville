# ANO-001 — Chaque appel à l'API via `http://localhost:8000` prend environ 2 secondes

Cas de test : REC-03 à REC-09 (exigence 7.1 du cahier des charges)          Statut : ouverte
Sévérité : S2          Priorité : P1
Constatée le 15/10/2026 par Mourad

## Environnement
Version `v1.0.0` (commit `dad729c`), base rechargée : oui (`schema.sql`,
`comptes.sql`, puis import en REC-01). Comptes `exploitant01` et
`direction01`. Windows 11, Python 3.14.7, PostgreSQL 18. API lancée avec
`uvicorn api.main:app --reload` (à l'écoute sur `127.0.0.1:8000`). `.env` :
`API_URL=http://localhost:8000`, valeur reprise de `.env.example`. Toutes
les routes de l'API sont concernées, et donc tous les écrans du front.

## Reproduction
1. Recharger la base, lancer l'API avec `uvicorn api.main:app --reload`.
2. Appeler `GET http://localhost:8000/sante` et mesurer le temps de réponse.
3. Faire le même appel sur `http://127.0.0.1:8000/sante` et comparer.

## Attendu / obtenu
Attendu : une réponse en moins de 2 secondes (cahier des charges, § 7.1 :
« toute consultation paginée répond en moins de 2 secondes »).
Obtenu  : chaque appel par `localhost` prend entre 2 023 et 2 335 ms
pendant REC-03 à REC-09, y compris `GET /sante` (2 079 ms), qui ne fait
aucun calcul. Le même appel par `127.0.0.1` prend 8 ms.

## Preuve
Mesure du 15/10/2026 09:13 :
```
localhost se résout en : ['::1', '127.0.0.1']
http://localhost:8000/sante -> 2066 ms
http://127.0.0.1:8000/sante -> 8 ms
http://localhost:8000/sante -> 2046 ms
http://127.0.0.1:8000/sante -> 8 ms
API à l'écoute sur : 127.0.0.1:8000 (pas sur ::1)
```
Temps relevés pendant la recette : voir `resultats-recette.md`, REC-03 à
REC-09 (par exemple `GET /stations?taille_page=50&page=1` → 2 049 ms).

Cause : sous Windows, `localhost` est d'abord résolu en IPv6 (`::1`). L'API
n'écoute qu'en IPv4 : le client attend environ 2 s l'échec de la connexion
IPv6 avant de passer à `127.0.0.1`. Le code de l'API n'est pas en cause
(8 ms de bout en bout en IPv4).
